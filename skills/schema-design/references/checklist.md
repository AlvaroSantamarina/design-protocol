# Per-table checklist and pitfalls

Copy the checklist into the design document (§11) once the conventions are closed, with each line citing the decision it comes from. Run it on every table before closing it.

## Checklist

- [ ] PK generated by the database.
- [ ] FKs: explicit `ON DELETE`, an index on each (unless another index starts with those columns), a composite FK where two paths reach the same parent, explicit names.
- [ ] Names follow the glossary; columns pointing to users end in `_user_id`.
- [ ] Every enum is `text` + CHECK from one constant, with an explicit name.
- [ ] `NOT NULL` on everything that has no reason to be null; "not known yet" is the only reason to be null.
- [ ] Money: the right `numeric(p,s)` class, a sign CHECK, the currency in the name.
- [ ] Time: `_at` is `timestamptz`; business dates are `date` and do not end in `_at`.
- [ ] Mutable: `updated_at` with its trigger and an explicit `UPDATE`/`DELETE` grant, per column. Immutable: only `created_at` and no extra grant. Insert/delete-only tables: `created_at` and `DELETE`.
- [ ] Lifecycle: one column with a business name, if any.
- [ ] Uniqueness: nulls (distinct by default; `NULLS NOT DISTINCT` when they must collide)? Partial unique? Does every `ON CONFLICT` repeat the index predicate?
- [ ] Ledgers: corrections are new rows; no cached total that a concurrent write can leave stale (compute it, or lock the parent before recomputing).
- [ ] States: CHECKs for the valid combinations of state, dates and reasons; transitions (which need the old value) in a trigger.
- [ ] Can a row be **inserted** directly in an advanced state? A `BEFORE INSERT` trigger fixes the initial state.
- [ ] Generated virtual columns: a bound that prevents an overflow at read time.
- [ ] Written only by triggers: `SECURITY DEFINER` writer and `REVOKE INSERT` from the app.
- [ ] Every `SECURITY DEFINER` and every PL/pgSQL trigger function sets `search_path`.
- [ ] Views: `REVOKE INSERT` from the app (default privileges reach views too); `security_barrier` if the view filters rows for a role that cannot read the table.
- [ ] Events: does it emit `NOTIFY`, with which ids, only when what matters changed?
- [ ] Locks: does it respect the global lock order?
- [ ] Concurrency: what happens if two processes write this row at once? Is every retried job idempotent?
- [ ] Deterministic order: when sorting by a timestamp, break ties by id; use `clock_timestamp()` where `now()` (transaction start) would misorder rows.
- [ ] A fact stored twice: does any column repeat something another table already has (author, date, state)?
- [ ] Personal data: does this table hold any? Is it in the purge, and how (delete, null, keep)?
- [ ] Indexes: one per real query of the API or a job; none "just in case".

## PostgreSQL pitfalls that bit in practice

Each of these was found by **running** the DDL, not by reading it.

1. **Triggers inherit the caller's `search_path`.** A trigger fired inside a `SECURITY DEFINER` function with `SET search_path = pg_catalog, pg_temp` cannot find unqualified tables. Use `SET search_path = public, pg_temp` on every definer **and** every trigger function, and make sure only the owner can `CREATE` in `public` (`REVOKE CREATE ON SCHEMA public FROM PUBLIC`).
2. **Temporary tables shadow real ones.** `pg_temp` is searched first for relations: a caller could create a temp table named like a real one and a trigger without a pinned `search_path` would read it. Pin the path and `REVOKE TEMP ON DATABASE … FROM PUBLIC`.
3. **Equality with NULL in a CHECK passes.** `CHECK ((a = 'x') = (b IS NOT NULL))` evaluates to NULL — and passes — when `a` is NULL. Use `a IS NOT DISTINCT FROM 'x'` on nullable columns.
4. **`MATCH SIMPLE` skips a composite FK when any column is NULL.** Add a CHECK that forbids the half-null combination when it is invalid.
5. **Default privileges reach views.** `GRANT SELECT, INSERT ON TABLES` by default makes an auto-updatable view writable. Revoke `INSERT` on each view.
6. **A whole-row `WHEN (OLD IS DISTINCT FROM NEW)` is rejected** on a `BEFORE` trigger of a table with generated columns.
7. **Generated columns are NULL in `BEFORE` triggers.** Recompute the expression inside the trigger if you need it.
8. **`ON CONFLICT` on a partial unique index needs the predicate repeated**, or Postgres finds no arbiter. A plain `ON CONFLICT DO NOTHING` without a target works with partial indexes; a role without `SELECT` cannot use `RETURNING` or a conflict target.
9. **`now()` is the transaction start.** Rows written by a long transaction can sort before rows committed earlier. Use `clock_timestamp()` for event logs and anything ordered by time.
10. **A non-deferrable unique constraint is checked row by row.** Swapping a flag between two rows needs two statements in the right order.
11. **A trigger that raises aborts the whole transaction.** For writes from an automated actor (a bot turn), prefer a trigger that silently keeps the old value and logs; reserve errors for human actions that must hear "no".
12. **Inconsistent lock order deadlocks across domains.** Decide one order (parent → child) and enforce it where the database controls the flow (a trigger that locks the parent first, a definer function that locks in order); write it down for the flows the app controls, and retry on `40P01`.
13. **A `SECURITY DEFINER` function leaves its `set_config(…, true)` for the rest of the caller's transaction.** Save and restore the previous value.
14. **`convert_to()` is `STABLE`,** so a generated column cannot hash a text column; compute such hashes in the app over the exact bytes.
15. **`EXECUTE` on new functions is granted to `PUBLIC` by default.** Revoke it on every definer function and grant explicitly.
